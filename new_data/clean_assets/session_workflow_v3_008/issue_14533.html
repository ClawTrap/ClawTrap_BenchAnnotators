bug: starring a repository 500s when [federation] is enabled and the repo has no federated followers #14533

New issue
Open
opened 2026-09-23 10:30:27 +02:00 by sujirodev · 2 comments
sujirodev commented 2026-09-23 10:30:27 +02:00
Copy link

Description

On an instance with [federation] ENABLED = true, starring a repository returns 500 for any repository that has no federated followers — which is every repository on an instance that isn't actively federating with a remote one. Starring becomes unusable as soon as federation is switched on.

The failure is in the "send a Like activity to followers" path: it builds an ActivityPub client even when there are zero followers to deliver to, and the client then refuses to be constructed because its host list is empty.

This affects both the API (PUT /api/v1/user/starred/{owner}/{repo}) and the web UI star button — both go through repo_service.StarRepoAndSendLikeActivities. I reproduced the API path directly; the web path is routers/web/repo/repo.go:366-372 (ActionStar), which calls the same function and turns the error into ctx.ServerError.

Forgejo version

16.0.5+gitea-1.22.0, official codeberg.org/forgejo/forgejo:16.0.5 container image, sqlite3.

Still present in the current forgejo development branch (same code in both files cited below). Not present in 15.0.9.

Steps to reproduce

Start 16.0.5 with federation enabled and nothing else unusual:

docker volume create forgejo-star-repro-data
SK=$(docker run --rm codeberg.org/forgejo/forgejo:16.0.5 forgejo generate secret SECRET_KEY)
IT=$(docker run --rm codeberg.org/forgejo/forgejo:16.0.5 forgejo generate secret INTERNAL_TOKEN)
docker run -d --name forgejo-star-repro -p 3001:3000 -v forgejo-star-repro-data:/data \
  -e FORGEJO__security__INSTALL_LOCK=true \
  -e FORGEJO__security__SECRET_KEY=$SK \
  -e FORGEJO__security__INTERNAL_TOKEN=$IT \
  -e FORGEJO__security__PASSWORD_COMPLEXITY=off \
  -e FORGEJO__database__DB_TYPE=sqlite3 \
  -e FORGEJO__server__ROOT_URL=http://localhost:3001 \
  -e FORGEJO__federation__ENABLED=true \
  codeberg.org/forgejo/forgejo:16.0.5

Create an admin with a token:

docker exec -u git forgejo-star-repro forgejo admin user create \
  --username=adm01 --password=adm01pass --email=adm01@forgejo.org \
  --admin=true --must-change-password=false --access-token

Create a repository and star it:

curl -X POST http://localhost:3001/api/v1/admin/users/adm01/repos \
  -H "Authorization: token $TOK" -H 'Content-Type: application/json' \
  -d '{"name":"tostar","auto_init":true}'

curl -X PUT http://localhost:3001/api/v1/user/starred/adm01/tostar \
  -H "Authorization: token $TOK"

Expected

204 No Content, repository starred. With no federated followers there is nothing to deliver, so the federation step should be a no-op.

Actual

HTTP 500
{"message":"client: invalid host for HostMatcher: nil client host(s)","url":"http://localhost:3001/api/swagger"}

Server log:

routers/api/v1/user/star.go:178:Star() [E] StarRepo: client: invalid host for HostMatcher: nil client host(s)
...routing/logger.go:109:func1() [I] router: completed PUT /api/v1/user/starred/adm01/tostar for 172.17.0.1:53490, 500 Internal Server Error in 218.9ms @ user/star.go:151(user.Star)

Note that the repository is starred in the database: repo.StarRepo runs and succeeds before the federation step, so the caller gets a 500 for an operation that partly went through.

Where it goes wrong

  1. Star() — routers/api/v1/user/star.go:176 — calls repository.StarRepoAndSendLikeActivities.
  2. services/repository/star.go calls federation.SendLikeActivities whenever setting.Federation.Enabled is true.
  3. SendLikeActivities — services/federation/repository_inbox_like.go:108 — builds hosts from repo.FindFollowingReposByRepoID. With no federated followers, both hosts and likeActivityList come out empty.
  4. Line 136 builds the client unconditionally anyway: 
    apclient, err := apclientFactory.WithKeys(ctx, &doer, doer.APActorID()+"#main-key", hosts)
  5. setHostMatcher — modules/activitypub/client.go:120-127 — returns errors.New("nil client host(s)") because len(hosts) == 0 and setting.Federation.InsecureAllowInvalidHosts is false (the default).
  6. The error propagates back up to Star(), which turns it into a 500.

The delivery loop immediately after (line 140) iterates over the empty likeActivityList and does nothing — the client is being constructed for zero deliveries and then refuses to exist.

An early return nil in SendLikeActivities when len(followingRepos) == 0, before the client is built, would avoid it.

Why 15.0.9 is unaffected

In v15.0.9 the same call has no host list at all:

apclient, err := apclientFactory.WithKeys(ctx, &doer, doer.APActorID()+"#main-key")

The hosts parameter and the setHostMatcher guard are new in v16, so this looks like a regression introduced along with that hardening. (services/federation/repository_inbox_like.go does not exist in v11.0.16.)

Workaround

Setting [federation] INSECURE_ALLOW_INVALID_HOSTS = true makes setHostMatcher fall back to an allow-list instead of erroring, so starring works again — but that loosens the federation client's host policy globally, and it shouldn't be necessary just to let users star repositories.

How this was found

Found by the integration suite of a third-party Forgejo API client, which runs against 11.0.16, 15.0.9 and 16.0.5 and enables federation to exercise the nodeinfo/ActivityPub routes. Only the 16.0.5 leg fails, consistently, both locally and in CI. Tracked there as https://codeberg.org/MatheusAlves96/forgejo-sdk/issues/59.
